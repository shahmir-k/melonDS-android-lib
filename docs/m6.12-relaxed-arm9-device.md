# M6.12 — Relaxed ARM9 Timing (plan §8) — results

Date: 2026-07-05
Flag: `LITEV_RELAXED_ARM9_TIMING` (default OFF). ARM7 timing untouched (WiFi invariant).
Branch: liteDS-v2. ROM: Shrek Smash n' Crash Racing (sha1 11d7849a…, the committed
`tools/headless/testroms/shrek.nds`).

## TL;DR — closed-negative

Relaxed ARM9 timing (DraStic-style flat cycles-per-instruction) is **implemented,
correct, deterministic, and the game runs a full live race under it** — but it is a
**performance REGRESSION on both host (−6.0% FPS) and the A55 device (−4.8% FPS; ARM9
bucket 7.76 → 9.11 ms, +17.3%)**, for a structural reason the plan's premise did not
account for:

> In this JIT, ARM9 timing is **baked at block-compile time** (the decode loop runs
> the interpreter once to fill `CurInstr.CodeCycles/DataCycles`; the emitted block
> just does `ADD RCycles, #const`). There is **no per-access MemTimings table walk in
> the ARM9 runtime hot path** to remove. Relaxing the model therefore does not delete
> runtime work — it only makes each ARM9 instruction advance sim-time *less*, which
> makes the game's **busy-wait / status-poll loops spin more times per real frame**.
> Measured: ARM9 u32-load helper calls **+23.6%**, ARM9 idle-loop hits **+51.7%**,
> scheduler iterations **+19.4%** → ARM9 exec time **+20.6%**, window FPS **−6%**.

This mirrors the M6.11 NEON-geometry outcome (landed, flag-gated, closed-negative).
The flag is committed OFF-by-default with its goldens so the result is reproducible
and the door stays open, but **it should not be enabled in the app.** See §5 for why
the brief's ranking of this front (built from the 7.55 ms ARM9 device bucket) did not
survive contact with the code, and what that implies for the 60 FPS campaign.

## 1. What was implemented

Single source of truth: under the flag, ARM9 (ARMv5) code-fetch and data-access cycle
costs become flat constants instead of a per-address `MemTimings` region-table walk.
The change lives entirely in the cost *source* — `ARMv5::CodeRead32` and the eight
`DataRead*/DataWrite*` functions in `src/CP15.cpp` — plus two named constants in
`src/ARM.h` (`kRelaxedArm9CodeCycles = 1`, `kRelaxedArm9DataCycles = 1`). Because both
the interpreter runtime and the JIT decode loop read `cpu->CodeCycles/DataCycles`, the
flat cost propagates automatically to:
- the interpreter's `AddCycles_C/CI/CD/CDI` (formulas collapse to flat with flat inputs),
- the JIT's compile-time-baked `Comp_AddCycles_*` constants (`CurInstr.CodeCycles/DataCycles`
  come from the decode loop), and
- `Comp_JumpTo`'s code-fetch cycle accumulation (uses `cpu9->CodeCycles`).

Side effect that *does* shrink emitted code: with flat `numC==numD`, `Comp_AddCycles_CD`
sets `IrregularCycles=false`, so conditional loads/stores fold into `ConstantCycles`
instead of emitting a runtime `ADD RCycles`. This is the only real emitted-code win, and
it is invisible next to the busy-wait amplification (§4).

Every edit is `#ifdef LITEV_RELAXED_ARM9_TIMING`; **all use sites gate on `Num==0`** so
ARM7 (and thus SPI/WiFi/RTC/MP timing) is byte-for-byte unchanged. Out of scope by
design and left exact: DMA9 unit timing (`DMA.cpp`, a separate 1.76 ms bucket) and all
ARM7 paths.

CMake: `option(LITEV_RELAXED_ARM9_TIMING … OFF)`, auto-exported PUBLIC via the existing
LITEV re-export loop. Android: additive `full-relaxed9` config in `tools/android-bench/build.sh`.

## 3. Semantic in-race check (flag-ON) — PASS

Full 3400-frame race script (`shrek-race.script`) under `build-relaxed9-full`: runs to
completion, no hang/crash, `fb_changing: yes`. PPM dump at frame 2601 (converted +
viewed): HUD **"4th" / "Lap 1/3"**, live 3D swamp track with Shrek's kart, race timer
running **"00:14.51"**, P1–P4 list, active minimap. The kart drives and the race is
fully live under relaxed timing. Flat-1 is not too aggressive for Shrek. (Mario-Kart-class
GXFIFO-interleave titles remain the standing watch item, untested — no ROM locally.)

Reading: the game's *real* ARM9 work is unchanged (identical GX command count, identical
block-transfer helper calls). What inflates is **status-polling**: the u32-load helper
(poll loops reading a status word) fires +23.6% more often and the ARM9 idle detector
trips +51.7% more, because flat-1 timing makes each poll iteration consume less sim-time,
so more iterations fit before the awaited event. That extra spinning is the +20.6% ARM9
and the −6% FPS. Host is only ~12% ARM9-bound, so this is the *mild* case.

geometry change (GX command count is unchanged).

## 6. Honest assessment vs the 7.55 ms ARM9 goal, and app FPS projection

The M6.12 premise (Appendix D.5): "flat cycles-per-instruction removes per-access timing
math including every GXFIFO write's accounting, which is where geometry cost lives." The
code does not support the premise on this JIT:

1. **The timing math is already compile-time-baked**, not runtime. The 8,451 GXFIFO
   writes/frame each cost exactly one baked `ADD` (or a folded `ConstantCycles`), set once
   when the block compiled. There is no per-write MemTimings walk at runtime to delete.
   The SlowWrite9 helper that actually performs a GXFIFO write does **not** touch cycles.
2. **Relaxing timing cannot remove runtime work here** — it only changes sim-time
   granularity, and finer granularity makes busy-wait/poll loops iterate more, which is
   net *more* ARM9 instructions per real frame (§4). The 7.55 ms bucket is dominated by
   the game's real instruction stream + memory moves + dispatch, none of which the flat
   model touches.

So M6.12 does **not** cut the 7.76 ms ARM9 bucket; it grows it to 9.11 ms (+17.3%) on
the A55. **Projected app FPS: no gain — a regression of ~−4 to −5%** (host −6.0%, device
−4.8%; vs the 24.97 FPS full-config baseline, relaxed9 = 23.93, −4.2%). The flag must
stay **OFF** in the app. It is committed OFF-by-default with reproducible goldens so the
negative result is durable and auditable, exactly as M6.11 NEON-geometry was.

Where the brief was wrong: it inherited D.5's assumption that per-access ARM9 timing math
is a *runtime* cost embedded in JIT execution. It is a *compile-time* cost in this
architecture. A relaxed-timing win of the DraStic kind would require DraStic's structure
(timing computed in emitted code at runtime), which melonDS's JIT does not have — so
there is nothing for the relaxation to reclaim.

**60 FPS path implication:** the emulation-side ARM9 bucket is not reachable by timing
relaxation. Remaining evidence-ranked levers are the reserve-tier structural ones already
noted in D.5 (batched GXFIFO drain / clipping restructure; hot-region recompilation),
none of which this front unblocks. Recommend M6.12 be marked closed-negative in Appendix D
alongside M6.11's NEON-geometry.

```
# Gates 1-2 (OFF byte-identical)
cmake -S . -B build-gate1-off  -DLITEV_HEADLESS=ON -DBUILD_QT_SDL=OFF -DENABLE_OGLRENDERER=OFF -DENABLE_GDBSTUB=OFF -DCMAKE_BUILD_TYPE=Release

# Gate 3 (flag-ON golden)
cmake -S . -B build-relaxed9-min -DLITEV_HEADLESS=ON -DLITEV_RELAXED_ARM9_TIMING=ON -DBUILD_QT_SDL=OFF -DENABLE_OGLRENDERER=OFF -DENABLE_GDBSTUB=OFF -DCMAKE_BUILD_TYPE=Release

# Device

```
