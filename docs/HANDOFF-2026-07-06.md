no overlap window), R3 GL diet (0% — cuts calls not content), R1 release build (0ms — no

## 3. The MEASURED performance reality (orchestrator-verified, not agent-claimed)
Device: Anbernic RG DS, 4×A55 @1.992GHz (throttles to ~1.6GHz @83°C within ~20s of the
CPU-heavy in-race scene — passive cooling, THIS is the sustained-FPS constraint).
- Heavy 8-kart in-race scene (slot-2 savestate), 3x GL, cooled start, ME-measured:
  R4 render thread ON = **~31 fps**; render thread OFF (inline) = **~31 fps**. IDENTICAL.
  runFrame (emulation, GL deferred) = ~24ms; the frame is EMULATION-BOUND, so render
  offload gives ~0 here. The earlier "55fps" (addendum 23) was a LIGHTER scene
  (runFrame ~14ms) where render was a real fraction — I over-reported it as the headline
  without verifying; on the heavy scene it does nothing.
- runFrame decomposition (headless A55): ARM9 ~18%, GPU3D ~5%, ARM7 ~4%, DMA ~4%,
  RunSystem ~63% (RunSystem = software rasterizer, HEADLESS-ONLY — the app uses GL). Of the
  app-relevant emu-compute, ARM9 dominates (~55%).
- Emulation-core wins measured on device (ARM9 exec ns/frame): SWTABLE −4.5→7.2%,
  SWTABLE+pin −7.4% vs fault-based fastmem. Real but ~0.5–0.8ms of frame.

Honest ceiling: sustained 60 @ 3x on the heavy scene is at/near the architectural ceiling.
DraStic hits 60 via a COUPLED architecture (branchless memory model + 15-reg global ABI +
software render across 4 cores) that reinforces itself; melonDS is already a strong JIT, so
individual DraStic techniques applied on top measure small. The coupled memory+register
change (SWTABLE+pin) is the first that pays off (−7.4%).

## 4. R4 render thread — DONE + CORRECT (the hard-won correctness story)
- The overlap is architecturally correct and PROVEN bit-exact via the on-device FBHASH gate
  (glReadPixels the composited output → per-frame hash → logcat; works on the RG DS GL
  hardware-overlay surface that screencap CAN'T read; deterministic via RTC-pin +
  frame-index-reset-at-loadState). Threaded == serial == flag-OFF, 250+ frames zero
  divergence (I re-ran this MYSELF: early-release 251/251 bit-exact).
- Root-cause races found+fixed: (a) deferred ReplayLog read the LIVE LogBuild pointer, not
  the replay bank → every-other-frame blank flicker (core fix); (b) raster read live emu
  geometry (poly flags) → snapshot into render-private storage.
- CRITICAL LESSON: screenshot/static-scene parity is INSUFFICIENT — it hid races that
  glitched under real gameplay. ONLY the FBHASH gate (bit-hash of the same deterministic
  frame, serial vs threaded) proves correctness. NEVER ship a render build the FBHASH gate
  hasn't passed. Two agents gave OPPOSITE (one false) claims about early-release; I settled
  it by running the gate MYSELF — it PASSES. Runtime props: debug.litev.renderthread (1=on),
  debug.litev.earlyrelease (1=on, the ~overlap), debug.litev.rtserial (1=force serial),
  debug.litev.fbhash (1=hash gate, ~16fps glReadPixels cost — OFF for real play/FPS).

## 5. Device / build gotchas (learned the hard way — obey these)
- **adb-injected game input is DEAD** on this device (only Android UI taps work). So render
  correctness is validated via the FBHASH gate on a DETERMINISTIC savestate (no input), NOT
  driven gameplay. The USER is the final visual check for real play.
- **AGP reuses STALE native .so** on source/cmake-arg changes. MANDATORY every app rebuild:
  `rm -rf app/.cxx app/build/intermediates/cxx && ./gradlew clean :app:assembleGitHubProdDebug`,
  then verify the packaged .so mtime > your edit. Multiple agents shipped stale binaries.
- **Torture goldens REQUIRE --input-script**: armwrestler-arm-600 + rockwrestler-600 verify
  ONLY with their scripts (tools/headless/baselines/*.script). Running verify WITHOUT the
  script diverges at frame ~201 (the script's first button press) — this caused a false
  "born-bad golden / regression" panic (addendum 17, RETRACTED in 20). The harness now
  hard-fails (exit 4) on script-hash mismatch.
- **Verify goldens YOURSELF, don't trust agent claims.** Agents in this campaign gave: a
  false "early-release fails gate" (it passes), a false "torture goldens pass" (stale build),
  stale-.so builds, and an over-reported 55fps. Re-run every gate. (Also: watch your OWN
  shell loops — a path-parsing bug in a verify loop gave false exit-1s; run goldens as
  individual commands.)
- Reinstall the user's fast build after measurement, DON'T leave the old baseline (agents
  kept restoring e3badc8, confusing the user). Leave a KNOWN-GOOD build on the device.
- Golden build recipe: `cmake -B build-host -DLITEV_HEADLESS=ON -DBUILD_QT_SDL=OFF
  -DENABLE_OGLRENDERER=OFF -DENABLE_GDBSTUB=OFF -DCMAKE_BUILD_TYPE=Release`. Host = Apple
  Silicon arm64 = the SHIPPED ARMJIT_A64 backend, so host goldens ARE the real codegen path
  (correctness fully gated on host; PERF is device-only — OoO host hides in-order A55 wins).
- Device FPS must be measured COOLED (force-stop, wait thermal_zone0 <52000, take FIRST
  ~30 LITEV_PROF lines). Slot-2 = the heavy 8-kart in-race deterministic demo. Gate scripts:
  scratchpad/fbgate2.sh, fbcmp2.py, fpsrun-cool.sh (may be wiped — reproducible).
