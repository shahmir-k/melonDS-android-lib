# M6.11 step 1 — RunFrame decomposition (host measurement)

**Goal:** decompose the ~20ms in-race `RunFrame` bucket (Appendix D.4) so the
GPU3D geometry engine's share is known before the NEON geometry work (M6.11)
starts. This measures on the **host** (Apple M3), so the *absolute* times are
irrelevant to the A55 target — the **shares / ratios are directional**.

## What was instrumented (LITEV_PROFILE only; compiles to nothing when off)

New `LiteProfile` counters + call sites carve `NDS::RunFrame()` into disjoint
per-slice buckets:

| bucket | counter | call site | what it is |
|---|---|---|---|
| RunFrame (parent) | `RunFrameNs` | `NDS::RunFrame()` scope | whole frame wall time |
| ARM9 JIT exec | `ARM9ExecNs` | wraps **only** `ARM9.Execute` | ARM9 code (excl. geometry + DMA) |
| GPU3D geometry | `GPU3DNs` | wraps `GPU.GPU3D.Run()` | GXFIFO command drain / vertex-matrix-clip-poly math |
| ARM7 exec | `ARM7ExecNs` | wraps **only** `ARM7.Execute` | ARM7 code (excl. DMA7) |
| DMA 9/7 | `DMA9Ns`,`DMA7Ns` | wrap the DMA `.Run()` blocks | channel DMA (incl. GXFIFO-DMA feed) |
| scheduler/events | `RunSystemNs` | wraps `RunSystem(target)` | scheduler event dispatch **+ host software rasterizer** (see caveat 1) |
| residual | `RunFrameNs − Σ(children)` | — | slice-loop overhead, NextTarget, GXFIFO-stall calc, RunTimers, StartFrame |
| GX command count | `GXCommands` | `GPU3D::ExecuteCommand()` | # GXFIFO commands executed (a cheap `++`, not a timer) |

**Nesting / double-count discipline.** The task brief warned that GXFIFO command
execution runs *synchronously inside ARM9 MMIO writes/DMA*. In **this** melonDS
core that is **not** the case: `CmdFIFOWrite` only *enqueues*; the geometry
commands drain later in `GPU3D::Run()`, which NDS.cpp calls **once per scheduler
slice, outside the ARM9 scope**. So `ARM9ExecNs` already excludes geometry math —
there is no ARM9↔GPU3D parent/child overlap to subtract. What `ARM9ExecNs` keeps
is the cheap FIFO-*enqueue* cost of the thousands of GXFIFO MMIO writes/frame,
which is legitimately ARM9-side work, not geometry. The one bucket that *was*
nested is DMA: `DMA9`/`DMA7` `.Run()` previously sat inside the ARM9/ARM7 scopes
and are now timed separately, so the CPU scopes wrap only `Execute`.

**GX-command timing distortion is made visible, not hidden.** `ExecuteCommand()`
runs thousands of times/frame, so a per-command `clock_gettime` would wreck
`GPU3DNs`. Geometry is therefore timed at the **`Run()`/FIFO-drain batch** level
and commands are only **counted** (`GXCommands`). `GPU3DNs / GXCommands` gives an
ns/command figure whose sanity exposes distortion (see caveat 3).

## Gates (both pass, bit-exact — profiling is observational only)

```

cmake -B build-host -DLITEV_HEADLESS=ON -DBUILD_QT_SDL=OFF -DENABLE_OGLRENDERER=OFF \

  --verify-trace tools/headless/baselines/shrek-600.trace          # -> OK, exit 0

# same config + profiler ON (separate dir)
cmake -B build-prof … -DLITEV_PROFILE=ON …  &&  cmake --build build-prof -j8
./build-prof/liteDS-headless … --verify-trace tools/headless/baselines/shrek-600.trace
                                                                    # -> OK, exit 0 (bit-exact)
```

Both the default build and the `LITEV_PROFILE=ON` build verify the golden trace
bit-exact for all 600 frames: the instrumentation does not perturb emulation.

## Host caveats (read before trusting any share)

1. **`RunSystemNs` is inflated by the host software renderer.** With
   `ENABLE_OGLRENDERER=OFF`, the 2D+3D **rasterizer runs on the CPU as scheduled
   `Event_LCD → StartScanline → DrawScanline` events inside `RunSystem`**. On the
   RG DS the GL renderer does this on the GPU, so RunSystem's 50–60% here **does
   not exist on the device**. Treat RunSystem + residual as "host-only overhead"
   and read the **emulation-compute buckets (ARM9 / GPU3D / ARM7 / DMA)** for the
   device-relevant picture.
2. **Apple M3, not A55.** Absolute ns are ~5–7× faster than the target and the
   M3's wide OoO core rebalances buckets differently than an in-order A55. Only
   ratios transfer.
3. **`GPU3DNs` carries a fixed per-slice `Run()`-dispatch cost.** `Run()` is
   called every scheduler slice (~9k/frame) and early-returns when the FIFO is
   empty. In an idle workload that no-op overhead *is* the bucket (see the boot
   table: 22 commands/frame but 0.13ms `GPU3DNs`). In-race, 8.5k commands/frame
   swamp it (32 ns/cmd), so the **in-race** geometry share is the meaningful one.
4. Two profiled configs are shown: the **default/exact-timing** config (matches
   the gated build) and an **EVENT_SLICES + MEM_FAST** config (closer to the
   device app flags in D.3). Both agree on the geometry ratio.

## Reading — where the geometry share lands

- **The GXFIFO command volume is the headline.** In-race the ARM9 issues **~8.5k
  GX commands per frame** (vs 22 in menus). That is the geometry engine being
  *hammered*, exactly as D.1 predicted, and it is the untouched slice M6.11 aims
  at. ns/command (~23–32 ns on M3) is stable and clock-distortion-free because it
  is measured at the FIFO-drain batch level.
- **Geometry is ~22–23% of real ARM emulation compute** (ARM9 + GPU3D + ARM7 +
  DMA), consistent across the exact-timing and EVENT_SLICES configs — the
  **second-largest** emulation slice after the already-JIT-optimized ARM9
  (~48%), and bigger than ARM7 or DMA individually. Nothing has ever optimized
  it, so it is the highest-leverage untouched target, which matches M6.11's
  premise ("the largest untouched slice of in-race emulation time").
- **Do not read the raw "share of RunFrame" as the device share.** On host,
  RunSystem (50–60%) is dominated by the **CPU software rasterizer** that the
  device does on the **GL/GPU**. Strip RunSystem + residual and the emulation
  core is ARM9 ≫ GPU3D > ARM7 > DMA.
- **Projecting to the A55's ~20ms RunFrame** (D.4, GL renderer so no software
  rasterizer inside RunSystem, and DTCM/fastmem in play): if the ~22–23%
  emu-compute geometry ratio holds, geometry is on the order of **~4–5ms of the
  in-race frame** — a large enough slice that NEON-ifying the vertex/matrix/clip
  math and batching GXFIFO command processing (M6.11's plan) can plausibly
  recover a meaningful fraction of the gap to the 16.6ms budget. This host run
  gives the *ratio*; the on-device profiler run (M6.11 step 2, device backend)
  must confirm the *absolute* ms before sizing the payoff.

**Bottom line for M6.11:** geometry is confirmed as the #2 emulation-compute
consumer in-race (~22–23%), it is driven by ~8.5k GXFIFO commands/frame, and it
is completely unoptimized — a well-aimed target for the NEON geometry front. The
absolute size (~4–5ms projected) must be pinned down on-device next.
